# 成员恢复与移出关联数据调查

创建日期：2026-10-27。范围：撤销移出、成员身份恢复、维修／志愿／值班、待办、EWA、消息及并发边界。本次为只读调查，未实现恢复功能，未修改业务代码或云端数据。

## 1. 结论

目前没有完整的撤销移出／恢复成员操作。前端无已移出名单和恢复按钮，后端无恢复 action，现有详情接口直接拒绝已移出用户。前一轮修复仅补齐日志集合及初始化，不包含恢复功能。

可以在现有数据基础上实现安全恢复：沿用同一条 `users` 身份记录和同一 openid，恢复组内身份与 `proUsers` 投影，保留当前业务表和 EWA。但当前不能直接承诺“一键无损撤销所有变化”：成员日志只备份成员投影和本次变更字段，没有备份全部关联任务，也不能撤销移出前为了交接而执行的取消报名、移除受理人或任务重新分配。

移出本身只降权、删除成员投影、增加审计；不会级联删除、转交或重置业务表。未完成的负责事项原则上应先交接，否则移出会被阻止。不过，还发现了移出后旧任务写权限、志愿报名身份校验、统计口径等缺口，不能把当前系统描述成已经具备完整的离组／恢复生命周期。

## 2. 证据范围

- 只读核对当前源码、前端入口和真实云端部署包。志愿活动、EWA、待办、值班共 15 个关键文件，以及维修任务 5 个关键文件，云端与本地哈希一致。
- 当前环境 `maintenance-group-2e9wxm620047ff` 中，`users.membershipStatus=removed` 数量为 **0**，`member_management_logs` 中 `action=removeTeamMember` 数量为 **0**。不存在可用于本次云端成功移出／恢复验收的样本。
- 已移出用户查询返回 0 条，与计数一致，无分页遗漏；没有把历史调查时点的状态直接当成当前状态。
- 复用上一轮成员管理 14 项通过证据，涵盖交接阻塞、移出保留历史及 EWA、旧权限码不能恢复等。该证据属于本地内存及 SDK 请求边界验证，不代表真实移出和恢复验收。
- 本轮按 test-scope 止于 L0：源码、部署包和数据库只读核查，没有为纯调查重跑已有测试，也没有调用可能回写状态的待办／汇总业务接口。
- 原始云端包、哈希核对和只读查询结果保存于已确认 Git 忽略的 `.eidos/member-removal-review/`。

## 3. 移出时各集合的实际变化

主入口见 [`memberManagement.js`](../../../cloudfunctions/users/memberManagement.js)：`ACTIONS` 第 6 行，交接检查第 75 行，身份更新第 163 行，删除投影第 172 行，投影备份第 195 行。

| 集合／数据 | 移出动作本身的处理 | 恢复时的原则 |
| --- | --- | --- |
| `users` | 保留原文档与 openid；设 `role=user`、`membershipStatus=removed`、`roleManaged=true`，写原因、操作者、时间，递增版本 | 原地恢复身份，保留离组期间本人更新的资料，不能新建另一账号 |
| `proUsers` | 删除投影；原投影完整保存在移出日志的 `memberBackup` | 基于当前账号资料与原投影重建，核对部门、应急联系人、部门切换时间，不盲目覆盖 |
| `member_management_logs` | 新增移出日志，保存受影响字段前后值、原投影、幂等标识 | 保留原日志，新增恢复日志并关联原移出记录 |
| `maintenance_tasks` | 不删除，不改变负责人、状态、姓名快照或 EW | 保留原 openid 关系；不抢回已交接任务，不重新打开已完成／取消任务 |
| `maintenance_toDo_list` | 移出本身不删除、转交或改状态 | 保留当前事实；独立核对主任务与待办状态是否一致 |
| `duty_slots / duty_toDo_list` | 移出本身不删除历史值班、不改时间、不结算或扣分 | 历史排班保留；未来安排重新按当前业务规则选择，不能自动恢复旧占用 |
| `voluntary_activities / volunteer_toDo_list` | 移出本身不删除参与记录、创建者关系、反馈、EW 映射或待办 | 保留历史活动；已经取消的报名或交接的职责不能自动重新加回 |
| `ewaSummary` | 移出不删记录、不清零、不重算，手动调整字段保留 | 保留恢复时的最新数值，不以移出时快照覆盖后续补记与更正 |
| 消息、反馈弹窗、推送日志 | 移出函数不处理这些集合 | 保留历史；若存在异常遗留提醒，应按实际业务状态处理 |

`memberBackup` 是 `proUsers` 的备份，**不是所有业务表的备份**。例如，先用“删除附加受理人”完成交接，会由该业务接口删除对应维修待办；先取消志愿报名，也会由取消接口改变报名表与待办。这些变化不属于成员移出事务，无法仅凭成员日志自动倒回。

## 4. 哪些事项会阻止移出

| 关联事项 | 当前拦截条件 | 需要如何处理 |
| --- | --- | --- |
| 主／附加维修受理人 | `taskStatus=pending/inProgress` 且本人为主或附加受理人 | 先按业务事实完成、取消或完成交接。附加受理人可用已有移除接口；该接口明确不允许删除主受理人 |
| 本人申请的报修 | 只有申请人关系、并非受理人时不阻止移出 | 普通账号仍可报修和处理本人申请，这是保留账号的正常能力 |
| 值班预选或确认 | `assignedUser/dutyHolderId` 属于本人，且结束时间在未来，或日期无法解析 | 先处理占用；已确认值班不能由本人自行撤销，按管理流程调整 |
| 志愿活动创建者／参加人 | 活动为 `pending/inPreparation/inProgress` | 先处理创建职责或参加关系，不能通过成员移出自动取消报名 |
| 已完成维修、已结束活动、过去值班 | 通常不阻塞 | 保留历史归属和计量，不为了离组清理历史 |

需要注意：普通“取消志愿报名”有活动前一天 17:00 的截止规则，不能把它当作任何时候都可用的交接入口。若现有界面无法处理真实交接，应完善专用交接流程，不能改状态伪造已完成来绕过移出保护。

## 5. 新发现的关联缺口

### 5.1 离组不等于所有业务写权限都已收回

已核对线上相同源码：

- [`updateMaintenanceTasks.js`](../../../cloudfunctions/maintenanceTasks/updateMaintenanceTasks.js) 第 57–59 行仍按“原主受理人”放行，不要求其当前仍在组；第 72 行展开传入更新字段，非组长仅删除 `ew` 等少数字段，没有完整状态迁移和字段白名单。原主受理人离组后，仍存在修改原任务的服务端路径，不能将历史只读权限与内部写权限混为一谈。
- [`registerForVolunteerActivity.js`](../../../cloudfunctions/volunteerActivities/registerForVolunteerActivity.js) 第 91 行只检查 `users` 资料存在，后续就进入报名事务，没有完整的在组身份检查。离组账号仍保留 `users`，因此隐藏菜单不能替代后端拒绝新增报名。
- [`batchImportVolunteers.js`](../../../cloudfunctions/volunteerActivities/batchImportVolunteers.js) 第 167 行的 `isLeader` 只用于是否绕过招募关闭条件；第 205 行从 `users` 读取目标，也没有完整拒绝离组目标。旧名单或直接请求可能重新写入离组人员的活动关联。

以上为部署源码确认的路径缺口，未向生产环境发起利用请求。应优先补齐“内部动作必须仍在组”的校验，同时保留普通账号作为报修申请人的正常权限。

### 5.2 移出与分配／报名没有统一并发保护

移出事务会查询当时的关联业务，但其他分配、报名接口没有共同的成员写锁。存在“身份检查时仍在组，随后发生移出，旧请求最后落库”的竞态风险。单纯多查一次角色不足以证明不存在此窗口。

建议让新增任务、志愿报名／导入、值班安排与移出使用一致的身份状态和并发保护，并在移出事务完成后复核目标是否仍有新产生的进行中关联。调查没有把这一风险表述为线上已经发生的数据事故。

### 5.3 主表交接检查没有覆盖所有待办异常

交接检查查询三类主业务表，不直接检查 `*_toDo_list` 是否存在孤立记录、重复记录或过期状态。主任务已完成但待办仍为进行中时，移出可以成功；待办可能继续显示或计数。

[`getTodoList.js`](../../../cloudfunctions/userToDoList/getTodoList.js) 仍按 openid 读取历史数据，部分查询还会同步状态或清理不存在活动的孤立待办。移出后本人前端只显示维修分类，隐藏值班与志愿分类，见 [`todo/index.js`](../../../miniprogram/pages/user/todo/index.js) 第 65、99 行。因此“页面看不到”不能作为记录已删除的证据；恢复身份后，保留的记录可能重新显示。

对正常历史记录无需额外清理；对状态不一致记录，应以主业务事实核对和归档，不批量删除。若要求离组人员继续查看自己的志愿／值班历史，应另补只读入口。

### 5.4 EWA 排名、导出、更新汇总的人员口径不同

- [`getRanking.js`](../../../cloudfunctions/equivalentWorkloadAssessment/getRanking.js) 第 76、122 行直接查询含 `ewaUserId` 的汇总记录，没有按当前成员身份过滤。离组者的汇总保留后，仍可能参加排行榜。
- 实际 `exportExcel` action 被 [`index.js`](../../../cloudfunctions/equivalentWorkloadAssessment/index.js) 第 33 行分发到 `exportAdvancedExcel`；该实现第 94 行读取 `proUsers`，按当前成员生成导出行，移出后不再包含该人。
- [`updateSummary.js`](../../../cloudfunctions/equivalentWorkloadAssessment/updateSummary.js) 第 61 行按当前成员投影逐人重算，移出者不在这一批更新中，但其已有汇总不因此删除。

所以会出现“排名仍有此人，当前成员导出没有此人”的口径差异。需要明确当前组员统计与历史贡献统计的边界，分别标注和筛选；不能为统一显示而删除离组者 EWA。

### 5.5 保留 EWA 不代表移出后冻结不变

交接只看值班结束时间，不要求过去值班已经完成后台结算；已结束志愿活动也不要求已设置最终 EW。历史结算可能在离组后继续发生：

- [`dutyStatusManager.js`](../../../cloudfunctions/dutySchedule/dutyStatusManager.js) 第 58 行按历史值班归属结算，不依赖 `proUsers` 存在。
- [`setParticipantsEW.js`](../../../cloudfunctions/volunteerActivities/setParticipantsEW.js) 第 52、88 行按历史参加名单和现有汇总补记或调整，不要求目标当前仍在组。

这类按已发生业务补记不应因离组被一刀切删除。恢复时必须保留最新账目，不能恢复旧 EWA 快照。建议在移出核对信息中说明未结算事项；必要时先结算，但不能重复发分。

### 5.6 值班锁与提醒不由移出统一清理

移出未单独处理仅有 `lockUserId` 的锁记录或异常锁归属，正常预选中的分配字段会触发阻塞，但纯锁或异常历史锁不在该查询条件内。过期锁有独立清理机制；不建议为恢复成员重新激活旧锁。

提醒调度主要按值班分配／活动参加关系选择接收人，没有成员移出事件统一撤回提醒。正常未来安排会阻塞移出；若因并发或异常遗留关联，仍可能继续通知。应处理异常关联及待发送任务，而非删除历史消息。

## 6. 安全恢复应包含什么（建议，未实现）

1. 提供仅管理者可见的已移出名单、详情和恢复入口，展示原移出原因、时间、角色以及可恢复的投影字段。
2. 以原用户 ID 和 openid 为身份锚点，校验唯一性、当前移出状态、当前版本与最后一次有效移出日志；拒绝身份冲突、投影重复或备份不匹配。
3. 一个事务中恢复明确选择的组内角色、解除有效的移出状态、递增版本、重建成员投影并新增恢复日志，保留原移出审计。默认按组员恢复；原组长／管理员身份的恢复需要明确选择和后端授权。
4. 使用当前 `users` 的姓名、学号、QQ、头像等最新资料；只对账号中没有的部门、应急联系人、部门冷却等投影信息使用备份并核对。应急联系人重新启用需明确确认。
5. 不新建账号、不更换 openid、不复制整份旧用户覆盖当前记录；保留全部业务表的当前状态与最新 EWA／manual 字段。
6. 不重新开启已结束任务、不撤销已经完成的交接、不自动恢复已取消报名或旧值班占用；若确需重新安排，作为新的业务操作审计。
7. 恢复请求支持稳定幂等标识、重复点击和网络重试；恢复后刷新本人角色、tab、成员列表和统计口径。
8. 缺少原投影备份或存在异常数据时，先只读预览与备份受影响记录，再决定人工补齐；不静默拼造“完整历史”。

只改 `users.role` 无法恢复：`membershipStatus=removed` 仍被管理接口、登录和投影同步拒绝。只补 `proUsers` 也不行，身份同步会再次移除它。即使人工同时改这两处，也缺少版本、幂等和恢复审计，不能称为完整安全操作。

## 7. 建议实施优先级

1. 先补旧维修任务写权限、志愿报名／导入的服务端身份保护及新增关联的并发边界，确保离组状态有效。
2. 再实现成员身份恢复事务、名单与审计，按“恢复身份且保留当前业务事实”验收。
3. 同步明确当前成员与历史贡献统计口径，补移出前后的关联状态核对；正常历史任务与工作量继续保留。

本轮交付是调查结论与建议。恢复功能、上述关联缺口的修复、真实测试身份的完整移出／恢复验收均尚未实施。
