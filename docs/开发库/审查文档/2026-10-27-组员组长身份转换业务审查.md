# 组员与组长身份转换业务审查

创建日期：2026-10-27。

> 后续状态：本文保留修复前的发现与证据。五类问题的代码修复和 L1／L2 验证见 [身份转换边界修复记录](../开发日志/2026-10-27-身份转换边界修复.md)；生产部署、真机与云端联调状态以该记录为准。

审查对象：当前工作区源码，包括本次审查开始前已有的未提交改动。本文是代码审查与本地定向验证记录，不代表线上部署状态。此次未修改业务代码、未访问生产数据库、未部署。

## 1. 结论

确认 5 类问题，其中 2 类建议优先修复。角色转换事务自身有版本、幂等与双集合保护，主要缺口在降权后的业务权限、在途请求及客户端状态同步。

| 编号 | 优先级 | 问题 | 证据 |
| --- | --- | --- | --- |
| R1 | P1 | 降为组员后仍能清空、重新生成值班数据 | 源码及内存执行复现 |
| R2 | P1 | 降权后的任务当事人仍能修改任务状态和受理人，绕过专用操作 | 源码及内存执行复现 |
| R3 | P2 | 最后一名在职管理者可以自降权，导致系统内无人能恢复管理权限 | 源码及内存执行复现 |
| R4 | P2 | 代分配请求通过旧组长身份校验后，降权仍可能提交成功 | 源码及确定时序的内存复现 |
| R5 | P2 | 身份刷新完成后，当前团队页仍可显示旧角色入口 | 真实 App/Page 方法的生命周期模拟复现 |

R1、R2 是相关业务接口原有的权限缺口，并非角色变更事务直接造成；增加身份调整功能后，不能再假设隐藏管理入口就能完成降权。

## 2. 实际业务链路

1. 管理详情通过 `changeRole` 计算目标角色，展示确认框，经 `apiAdapter` 提交 `changeMemberRole`。
2. `users/memberManagement.handle` 从微信上下文识别操作者；仅在职 leader/admin 可以管理。
3. 事务内重新读取操作者和目标，校验版本、请求标识与成员投影；目标及新角色都限于 member/leader。
4. 在同一事务中更新 `users.role`、`roleManaged=true`、版本，以及 `proUsers.role` 和审计日志。
5. 本人降权时刷新身份并返回上一页；调整别人时，通知只通过本地 `membersChanged` 事件发布，目标设备没有实时收到身份变更事件。
6. 登录认证保留现有内部角色，旧权限码不会覆盖管理调整。后台回前台时异步刷新本人信息。

入口：[page.js](../../../miniprogram/pages/team/members/page.js)、[memberManagement.js](../../../cloudfunctions/users/memberManagement.js)、[login/index.js](../../../cloudfunctions/login/index.js)。

## 3. 已确认问题

### R1：值班破坏性操作没有落实组长权限

位置：

- [clearAllDutySlots.js](../../../cloudfunctions/dutySchedule/clearAllDutySlots.js) 第 144—147 行，权限检查仍为 TODO，实际跳过。
- [regenerateDutySlots.js](../../../cloudfunctions/dutySchedule/regenerateDutySlots.js) 第 197—198 行，同样没有执行权限检查。
- [dutySchedule/index.js](../../../cloudfunctions/dutySchedule/index.js) 第 53—69 行，入口对写操作检查退休状态，没有统一检查组长角色。

场景：组长被调整为在职组员后，仍可直接请求这两个 action；旧页面中尚未失效的按钮也可能继续走原路径。此问题甚至不以曾经担任组长为前提。

影响：清空值班时间段、其他人的值班待办；清空流程还包含工作量扣除。重新生成可以插入排班数据，造成重复或异常配置数据。`forceDelete=false` 也不会使服务端真正检查权限。

复现：使用现有内存数据库，真实 `retirementBlock` 对在职组员返回不阻断；真实清空函数返回 200，并删除其他人的模拟待办。真实重新生成函数对组员返回 200，插入 35 条模拟时间段。此处没有实际执行云函数网络入口，入口分发关系由源码确认。

建议：为每个破坏性 action 加入基于 `users` 当前身份的在职 leader/admin 校验；客户端参数不能绕过鉴权。同模块 `forceReleaseUserLocks` 直接接受目标 userId，且没有操作者/他人边界，也应一并收口，避免组员释放他人的锁；该附加路径本次仅作静态确认。

### R2：维修任务通用更新接口允许改写敏感业务字段

位置：[updateMaintenanceTasks.js](../../../cloudfunctions/maintenanceTasks/updateMaintenanceTasks.js) 第 57—88 行。

场景：组长降为组员后，若仍是某任务申请人或主受理人，继续满足该接口的当事人条件。接口将客户端 `updateData` 整体展开，只移除已废弃字段及非组长传入的 `ew`。

影响：当事人可以直接写入 `taskStatus`、`assigneeId`、`additionalAssignees` 等，绕过完成确认、分配和协助受理人接口的规则。主任务改变受理关系后，待办仍按变更前的任务当事人同步，容易出现记录与责任人不一致；受理关系与完成状态也会影响后续工作量计算。不能将这个问题描述成能够直接修改 `ew`，该字段已有单独过滤。

复现：在职 member 为任务主受理人时，真实函数接受 `taskStatus=completed`、替换主受理人和添加协助受理人的请求，返回 200；没有走申请人/组长的完成确认。相同请求里的 `ew=999` 被正确过滤，原 `ew=10` 保留。

建议：按操作者和业务动作定义允许更新的字段；状态、受理关系、结算字段由所属专用接口维护。不能只在通用接口增加一项角色判断，仍需明确普通当事人的字段边界。

### R3：最后一名管理者自降权后无法通过小程序恢复

位置：[memberManagement.js](../../../cloudfunctions/users/memberManagement.js) 第 170—174 行；[login/index.js](../../../cloudfunctions/login/index.js) 第 37—43 行。

场景：团队没有其他在职 leader/admin，最后一名组长将自己调整为 member。此请求允许成功，代码没有“至少保留一名可管理成员”的检查。没有其他在职管理者时，其他组长被逐个降权后也会进入同一结果。

影响：后续所有组员管理请求都被拒绝；旧组长权限码也不能把已管理的身份恢复为 leader，只能依靠云端人工维护。如果此时还有未完成活动或管理事项，将同时失去正常的处理入口。

复现：去掉内存数据中的管理员后，唯一组长自降权成功；剩余 leader/admin 数量为 0，原操作者读取管理名单返回 403；重新验证有效组长权限码仍返回 member。

建议：在变更事务中保留至少一名在职管理者，或先完成继任者任命。若允许多人同时自降权，需要共享的并发保护，不能仅在事务外统计人数。有管理员账号但其已退休，也不能算作可用兜底。

补充业务冲突：部分活动、维修接口仍只接受 `role === 'leader'`，并没有按角色层级接受 admin。因此“还剩管理员”能保证重新任命，但不代表管理员可以直接接管全部业务操作。

### R4：在途代分配请求使用了过期的组长授权

位置：[assignMaintenanceTask.js](../../../cloudfunctions/maintenanceTasks/assignMaintenanceTask.js) 第 31—35、91—101 行；[memberStatus.js](../../../cloudfunctions/maintenanceTasks/memberStatus.js) 第 52—68 行。

确定触发时序：

1. A 仍为 leader，发出替 B 分配任务的请求，事务外组长校验通过。
2. 另一管理者将 A 降为 member，双集合身份变更提交。
3. 原请求才进入 `withActiveMembers`，读取到 A 是在职 member。
4. 事务内只要求 A 是在职内部成员，没有重验“替别人分配必须是组长/管理员”，所以仍然成功分配。

这不是“两个事务同时写同一个 users 文档”时才出现的冲突：复现中的降权已经在分配事务开始前完成，现有写冲突机制不会补上缺失的角色判断。

复现：仅在现有内存数据库的 `startTransaction` 前插入一次已提交的降权，真实分配函数返回 200，提交时操作者为 member，任务却已分配给其他成员。

建议：在分配事务内依据本次读取的当前操作者角色，重新校验代分配权限，并保留与角色调整共写身份文档的保护。同类“先查组长、稍后写入”的操作需要逐项按其业务权限核对；本次不声称所有同类接口都已动态复现。

### R5：后台回前台时角色和页面状态可能不一致

位置：[app.js](../../../miniprogram/app.js) 第 123—126、209—237、404—416 行；[team/home/index.js](../../../miniprogram/pages/team/home/index.js) 第 103—124 行；[router.js](../../../miniprogram/utils/router.js) 第 82—112 行。

场景：用户停留在团队页，后台期间被别人调整角色。App `onShow` 发起异步身份刷新，Page `onShow` 先用旧全局角色计算入口。请求返回后，`updateUserRole` 更新全局与 storage，但 member/leader 的 tab 路径相同，不会发布 `tabsChanged`，团队页也没有订阅身份变更。

影响：升为组长后仍看不到管理入口；降为组员后继续显示旧入口，直至再次触发页面角色检查。持续停留前台时也没有远端角色变更推送或定期刷新机制。服务端正确鉴权的接口仍会拒绝越权，但 R1 的漏鉴权接口不能依赖此兜底。

复现：执行真实 App 和团队 Page 的 `onShow`、`refreshUserInfo`、`updateUserRole` 方法，延后模拟身份响应；分别模拟 member→leader、leader→member。全局角色都已变为新值，当前页面角色仍为旧值，角色更新阶段没有事件通知。

建议：身份更新发布独立的角色/身份事件，相关页面订阅并重算权限，管理页及时退出或收起操作。角色事件不应依赖 tab 路径是否发生变化。此项是状态正确性建议，不涉及视觉样式改造。

## 4. 未发现直接数据损坏的场景与已有保护

| 场景 | 当前处理 | 证据边界 |
| --- | --- | --- |
| member→leader→member | 更新角色与版本，保留投影 ID、部门及既有 EWA 字段 | 本次定向往返验证 |
| 普通组员或退休管理者调用角色调整 | 后端拒绝，不能靠伪造操作者字段通过 | 源码、现有权限用例 |
| 调整为 user/admin 或修改 admin 角色 | 角色调整入口拒绝 | 源码、现有用例 |
| 多个管理操作使用同一旧版本 | 后提交返回版本冲突，要求刷新 | 源码、内存串行事务用例；不是云端并发隔离实测 |
| 超时后重复相同请求 | 请求标识和日志提供幂等，内容不同则冲突 | 源码、现有用例 |
| 日志写入失败 | 身份、投影、版本随事务回滚 | 本次现有故障注入用例 |
| 个人资料写入与登录 | 个人资料白名单保留身份；登录不按旧权限码覆盖管理角色 | 源码、现有用例 |
| 未完成任务、已确认值班、志愿报名 | 单纯调整角色不删除或重新创建这些数据，member/leader 均保留成员身份 | 角色调整写入集合与字段的静态审查 |
| 退休人员调整角色 | 在职状态独立保留，不会因升为 leader 自动复职 | 角色调整增量字段与在职校验的静态审查 |

不要为降为组员自动清除值班、取消报名、重算历史工作量。角色变化并不等于离开团队。未结束活动的旧创建者会失去管理权限，但其他组长的活动管理接口没有绑定原创建者，能继续处理；需要关注的是交接和最后管理者消失，而非一律阻止所有有任务的成员降权。

## 5. 仍需业务确认或云端核对的边界

- 当前规范明确允许在职组长调整本人和其他组长，以及提拔组员。因此“组长可降另一个组长、可建立多个组长”是现有规则，不直接列为越权漏洞。若组织实际上要求管理员任免或限制部门范围，需要先调整权限规则。
- `completeMaintenanceTask` 在 `users` 不认定为 leader 时，会回退读取 `proUsers`，任一来源为 leader 即放行。当前角色变更事务同时写双集合，可避免正常路径产生半成功；但历史数据、手动维护或部署不一致形成旧 leader 投影时，仍有过度授权风险。应以 `users` 为身份权威，生产只读核查是否存在身份不一致后再判断实际受影响人数。
- 本次没有检查生产是否存在重复 openid、缺失投影、仍在运行的旧版本云函数、可用管理员，以及数据库客户端安全规则。不能依据本地代码认定云端数据已一致或线上漏洞已经被利用。
- 有管理员但没有 leader 时，多个只认 leader 的旧业务接口仍会拒绝管理员；建议统一角色层级判断，避免降权后出现“能任命但无法直接接管任务”的操作断层。

## 7. 建议处理顺序

1. 先封住 R1 值班破坏性接口和 R2 通用任务更新字段。
2. 再补 R4 在途管理操作的事务内角色校验，以及 R3 最后一名可用管理者保护。
3. 修复 R5 身份事件和页面状态收敛；同时核对管理员继承组长权限的一致性。
4. 修复时保留本次触发条件为最小回归用例，再做隔离测试账号的真实微信身份与云端事务验收，不使用真实成员试验降权。
