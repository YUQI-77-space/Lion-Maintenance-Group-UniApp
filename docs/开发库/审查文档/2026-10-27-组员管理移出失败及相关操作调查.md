# 组员管理移出失败及相关操作调查

创建日期：2026-10-27。调查范围：组员名单、详情、编辑资料、调整角色、移出成员、撤销移出与数据保留。本文记录本次只读调查，不代表修复或上线验收完成。

## 1. 结论

截图中的移出失败已由真实云日志定位：目标云环境缺少 `member_management_logs` 集合。管理写操作在事务内先读取该集合检查请求幂等性，读取即报错，还没有进入成员数据更新阶段。

资料编辑、角色调整、移出成员共用这个入口，因此三类写操作都受同一缺失集合阻塞。名单与详情查询不访问该集合，能够正常读取，形成“看得到成员，保存操作失败”的表现。

撤销移出／恢复成员目前未实现，不存在对应页面入口、action 或恢复脚本。现有业务文档明确排除了恢复入口。移出日志中的成员投影备份只供人工核对，不能视为已经具备恢复功能。

本次未修改业务代码、未创建集合、未修改云端成员资料、角色或规则，也未发布云函数。仅新增本调查记录；云端原始证据保存在 Git 忽略的 `.eidos/member-management-audit/`。

关键位置：

- [`memberManagement.js`](../../../cloudfunctions/users/memberManagement.js)：第 127 行开始事务，第 130 行读取日志；第 162 行才首次修改用户数据；第 185 行才写入审计日志。
- 同文件第 191–195 行将没有数字 `code` 的底层错误转为通用错误文本，前端照常显示，所以截图未暴露“缺少集合”。

## 5. 截图中目标成员的数据状态

通过姓名定位后，核对用户与成员投影的 openid 相同；仅查询必要字段，原始记录留在忽略目录，不在本报告公开身份标识。

- `users`：仍为 `member`，没有移出标记。
- `proUsers`：对应投影仍在，部门为电子技术部。
- `ewaSummary`：对应汇总记录 1 条；本次未对工作量数值做前后比较，不将“存在”表述为已核验全部数值。
- 按移出接口当前条件查询，未完成主／附加受理维修 0 条，未结束且关联本人志愿活动 0 条，关联值班记录 0 条，因此没有日期解析或未来值班待交接项。
- 全环境 `membershipStatus=removed` 的用户数量为 0。这只说明当前标记状态，不能据此否认历史上可能发生过其他方式的数据修改。

结合报错发生在首次写入之前，可确认截图对应失败请求没有完成降权或删除投影，当前无需为这次失败执行成员恢复。交接查询是调查时点快照，不替代未来实际提交时的重新校验。

## 6. 恢复功能的实际缺口

成功移出按当前代码会：保留 `users`，写入移出信息、`role=user`、`roleManaged=true`；删除 `proUsers`；在日志保留 `before / after / memberBackup`。历史业务和 EWA 并未删除，因此恢复成员身份通常不需要重建或重算历史工作量。

单独改回 `role` 不完整：`membershipStatus=removed` 仍会阻止管理详情访问和成员投影重建，登录也会将其继续视为普通用户。单独重建 `proUsers` 同样不完整，后续身份同步会再次删除它。

若后续增加恢复，至少需明确恢复目标角色，校验操作者、移出日志与当前版本，原子更新身份标记与成员投影，保留原移出审计并新增恢复日志，支持幂等与并发保护。不能直接把旧投影全量覆盖到当前资料，也不能重新计算或覆盖已有 EWA。此处为建议方案，尚未实现。
