# 现状审计与设计决策

> 历史审查记录。本文保留 2026-10-24 的代码证据、决策背景和待验证假设；当前规范以 [Design 目录](../../知识库/Design/README.md) 为准，实施顺序以 [前端设计美学重构优化计划](../设计文档/2026-10-24-前端设计美学重构优化计划.md) 为准。

审查日期：2026-10-24。范围：当前工作区的页面清单、公共样式、组件、导航、报修与任务相关代码。包含工作区已有的组员管理功能；不代表这些改动已经发布。

## 1. 已确认的现状

`miniprogram/app.json` 实际注册 31 个页面、4 个 Tab。普通用户显示首页／报修／我的，内部角色增加维修组；角色规则来自 `utils/router.js`。公共组件顶层目录有 8 个，其中 `charts` 含饼图、柱图两个组件。项目说明里的“29 页、7 个组件”尚未同步最近增加的成员模块与 `action-modal`。

本次静态扫描在 `miniprogram` 的 46 个 WXSS 文件中发现 156 种不同的十六进制颜色字面量：大小写归一，但 `#FFF` 与 `#FFFFFF` 尚未合并，包含主题、状态、图表和装饰色，不包含 RGBA 与 JS 内颜色。这个数字用于定位样式分散，不能直接视为 156 种有问题的颜色。

| 问题 | 代码证据 | 用户影响／需要验证的风险 | 目标决策 |
| --- | --- | --- | --- |
| 品牌蓝有多个来源 | `styles/variables.wxss` 的 `#0000CD`、`app.json` 的 `#3a75fb`、部分页面的 `#191970` | 跨页视觉身份不稳定 | 统一可读的品牌蓝和语义色，旧变量做兼容映射 |
| 多种表现语言并存 | `common.wxss` 线框按钮、`home/index.wxss` 图片头图、`custom-tab-bar/index.wxss` 玻璃层与多重阴影、`user/profile/index.wxml` 沉浸头部 | 主次与点击暗示不一致 | 浅色底面、白色信息区、单一实心主按钮 |
| 底部适配策略冲突 | `app.wxss` 的 `.safe-bottom` 设为 0，`.footer-fixed` 无安全区；首页／报修分别留 220rpx 底部空间 | 小屏、手势条、键盘场景存在遮挡风险，需真机验证 | 统一按实际导航／操作栏高度计算占位 |
| 组件能力与页面复用不一致 | 已有 `entry-item`、`section-header`、`action-modal`，页面仍有独立 `.function-item`、`.section-header` 与弹窗样式 | 修一个页面无法同步修复同类问题 | 先建立复用边界，再迁移高频结构 |
| 状态颜色来源矛盾 | `variables.wxss` 与 `activityStatusManager.js` 对志愿筹备中／进行中／已结束使用不同颜色 | 同一状态在不同页面含义不稳定 | 单一业务状态映射，文字与颜色一起输出 |
| 展示信息缺少行动入口 | `home/index.wxml` 的“我的待办”明确仅展示，条目无 `bindtap` | 看到事项后还要去“我的”找详情 | 待办条目进入对应详情，保留“查看全部” |
| 全页横滑承担 Tab 切换 | 首页、报修等绑定触摸事件，报修存在 `switchTab` 路径 | 与分类选择、输入、轮播等手势可能冲突 | 默认点 Tab 切换；取消整页横滑切 Tab |
| 任务中信息负担与步骤关系不清晰 | 报修已有搜索、三级分类、详情、核对、成功，内部步骤与顶部阶段不同 | 阶段感可能不一致；返回重选需确认数据保留 | 使用三个用户阶段，分类内部渐进选择 |
| 反馈方式混杂 | 报修提交使用系统 loading／Toast，成员管理复用 `action-modal`，其他页面存在 `wx.showModal` | 失败原因与操作后果可能转瞬即逝 | 错误放在发生位置，后果放在确认层，结果放在结果区 |
| 可靠性能力不能等同于完整业务闭环 | `outbox.js` 明确是未自动接入的能力；适配器发送 `_requestId` 并重试 | 不能向用户承诺所有写操作离线可提交或不会重复 | 各 action 验证幂等后再启用自动重放 |

以上是代码证据及其风险推断。没有截图、真机测量或用户测试的项目，不写成已经发生的线上故障。

## 2. 产品目标

| 人群 | 主要问题 | 设计成功的表现 |
| --- | --- | --- |
| 报修同学 | 不知道如何分类、要填什么、下一步何时发生 | 能搜索问题、理解费用说明、完成提交并找到进度 |
| 维修组员 | 工作入口分散、难判断哪个任务可处理 | 首屏看到待处理事项，详情知道当前状态与允许操作 |
| 组长／管理员 | 操作影响复杂、容易遗漏确认和交接 | 看清对象、修改内容、影响范围与阻塞原因 |

先保证任务完成与信息准确，再追求装饰效果。校园温度来自真实团队内容、易懂文案和有帮助的反馈。

## 3. 核心设计决策

| 编号 | 决策 | 理由与边界 |
| --- | --- | --- |
| D01 | 已由用户提供的官方标志确认主蓝为 `#0369D7`，主交互与品牌标识统一 | 横版与方形原图主体背景均为 RGB(3,105,215)，白字对比度 5.242:1；此前暂定交互蓝退出，历史页面蓝逐步迁移到此色系 |
| D02 | 浅色模式作为 v1 唯一验收主题 | 当前 `darkmode:false`；先把一套主题做完整，后续再定义深色映射 |
| D03 | TabBar 使用贴底白色底面，去除玻璃层、光晕和悬浮大胶囊 | 降低装饰比重，明确内容边界，减少额外底部空间计算 |
| D04 | 一级页统一自定义顶部栏，二级页优先原生导航栏 | 一级页保留品牌身份；二级页获得稳定返回与系统适配 |
| D05 | 一屏一个主要行动，相关信息按任务组织 | 重要操作应能被识别，不能让全部按钮同等强调 |
| D06 | 优先复用原生控件和现有公共组件，不新增大型 UI 框架 | 原生 WXML／WXSS 项目不引入 React、Tailwind、DOM 或字体网络依赖 |
| D07 | 关键结果始终区分“成功／失败／待核实” | 超时可能已经写入，不能提示用户盲目再次新建 |
| D08 | 内容列表优先自然滚动，只有必要表格允许局部横向滚动 | 取消团队首页禁用整页滚动；值班表可以固定时间列并横滚 |
| D09 | 官方标志保持蓝底白图形／白字的原始组合和比例 | 横版用于完整品牌展示，方形用于方形品牌位置；深浅蓝只供界面衍生，不对标志本身滤色、渐变或重绘 |

品牌确认依据为用户本轮提供的 `物科院维修组 (2).jpg`（9449×2362）与 `方形.jpg`（6250×6250）。在原图解码 RGB 像素中，`#0369D7` 分别约占 81.30% 与 91.10%，均为最高频颜色。JPEG 边缘附近的相近蓝属于压缩及抗锯齿差异，不另立品牌色。原图路径与文件 SHA-256 在 Token 文件的 `brandIdentity` 中留档，原图不复制到运行资源目录。

## 4. 需要验证的假设

- 报修分类是否易懂：邀请 3–5 位未参与开发的同学，用具体故障描述完成分类；记录误选路径和返回次数。
- 成员侧首屏优先级：以实际值班与任务频率决定工作台排序，不能把未确认的实时统计当作已有接口。
- 新的触控尺寸与字号：在 320／375／430 CSS px 宽度、系统大字体和键盘弹出时验证。
- 首页团队照片对信任的帮助：保留一张静态真实照片作为可选内容；不让自动轮播抢占任务入口。
- 全页横滑取消后的导航可发现性：观察用户能否直接用 Tab 切换，不增加教学遮罩作为默认补救。

## 5. 本轮范围

本轮安装设计 Skill 并建立文档、设计值和验收标准。没有修改业务页面、云函数、数据库或云资源。原 A–E 分批建议已由开发库中的新计划替代，不以一次全局换色代替流程改造。
