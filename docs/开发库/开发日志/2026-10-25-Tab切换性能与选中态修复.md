# Tab 切换性能与选中态修复

创建日期：2026-10-25。

## 调查结论与边界

用户反馈首次切换 Tab 时全屏短暂白灰、卡顿，连续点击不同 Tab 时图标错闪。本次源码确认了以下问题，但尚未取得真机渲染帧或性能数据，不能将其表述为白灰屏的全部根因。

- 自定义 TabBar 在 `setData` 的渲染完成回调内才调用 `wx.switchTab`，旧页渲染耗时直接延后导航启动。
- 每个 Tab 页面有独立 TabBar，原 `_switching` 只约束单个实例，目标页面出现后仍可与上一次未完成的导航并发。
- 点击后旧实例保留目标按钮的选中项，返回时需要再次纠正，存在显示错误中间态的风险。
- “我的”首次进入在 `onLoad` 和 `onShow` 重复调用资料与待反馈消息刷新，并重复提交未变化的角标数据。
- 本地图标单文件约 2～8 KB，启动页已有八个 Tab 图标预热，未发现图标体积异常的证据。图片解码、毛玻璃合成及设备端 WebView 创建耗时仍未测量。

## 已实现

- `custom-tab-bar/index.js`：选中项仍在一次 `setData` 中更新，随后立即启动导航，不再等待旧页面完成渲染；`pageLifetimes.hide` 恢复所属页选中项。保留角色化入口、反馈交互锁、双图层图标与失败恢复。
- `utils/router.js`：组件和既有路由入口共用导航锁，在原生完成／失败时释放；请求标识防止失败后的迟到回调解锁下一次导航。非法路径、当前页不重复导航，同步异常可恢复。
- 维修组权限回退、报修结果进入“我的”改用既有路由方法，共享防重。启动、登录等原有直接导航未在本次扩大重构。
- `app.json`：`window.handleWebviewPreload` 使用 `auto`，由微信在渲染线程空闲时预加载下一页 WebView。官方文档说明原默认策略是在 `onReady` 后 200ms 触发；本次采用平台空闲调度，未增加定时器、隐藏跳页或业务数据预取。尚无真机前后耗时对比，不能承诺首次白屏已消除。
- “我的”：资料与反馈刷新统一由 `onShow` 执行；导航同步移到刷新之前；角标只在变化时合并提交，保留回调和反馈弹窗锁。

外观与安全区维持当前实现；设计依据为 Design 的 01、02、04、06 及设计 Token。UI Skill 查询 `navigation active state flicker --domain ux`，仅采用 All 平台的 Active State 建议，未采用 Web 深链与布局示例。

## 未覆盖与验收方式

需在 iOS／Android 真机重新预览本地代码，冷启动后依次首次切换每个入口，再连续快速交替点击并回到已访问入口，检查页面与高亮一致性、首次空白帧和反馈弹窗交互锁。分别覆盖普通用户三入口、成员四入口，以及低性能设备。原生导航进行期间的点击会被防重忽略，完成后可再次点击，不排队重放旧点击。

当前结果属于已实现和本地逻辑验证，尚不属于真机流畅度验收。若仍存在白灰屏，需取得设备端页面切换／首次渲染耗时及截图帧，再定位 WebView 初始化、目标页首屏或毛玻璃合成的实际占比。
