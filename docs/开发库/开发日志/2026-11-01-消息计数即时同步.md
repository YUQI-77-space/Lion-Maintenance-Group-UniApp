# 消息计数即时同步

## 问题与改动

消息页在单条已读、全部已读和清空成功后，原先调用全局消息查询刷新徽标。该查询受 10 秒 TTL 限制，可能直接返回；即使执行，也要再获取一次全量消息，导致“我的”页徽标延迟。

新增全局 `updateUnreadMessageCount` 同步入口，消息页读取列表成功及写操作成功后直接使用已知未读数更新全局状态和既有个人页回调，更新 TTL，省掉冗余查询。失败时不改变计数。普通查询保留既有 TTL 与请求合并行为。

全局查询校验账号和计数版本，避免旧请求覆盖写操作后的计数。消息列表独立维护版本，避免旧列表覆盖清空结果，也避免全局查询正常完成时误丢弃列表。消息写操作增加互斥保护，防止重复提交及清空、已读相互覆盖。

## 实际验证

L0 已追踪消息页、全局计数、个人页回调及对应云函数契约；未修改云函数和数据库。

新增本地行为回归 `tests/message-count.test.js`，使用实际页面和 App 方法，仅隔离微信 API 与云函数网络边界：

- L1：`node --test --test-name-pattern='消息操作' tests/message-count.test.js`，7 项通过，最终运行约 100ms。覆盖三类操作成功／失败、TTL 内立即同步、无追加查询及重复点击后重试。
- L2：`node --test --test-name-pattern='跨页计数' tests/message-count.test.js`，5 项通过，最终运行约 87ms。覆盖旧全局查询、旧列表、空列表、并行正常查询及账号切换。

首次测试因测试模块作用域未隔离而加载失败，修复测试脚本后通过。后续独立消息列表版本调整使相关证据失效，按 L1、L2 顺序重新验证通过。
