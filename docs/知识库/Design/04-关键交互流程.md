# 关键交互流程

本文件定义目标体验。草稿恢复、结果核实等能力只有在真实可用时才能向用户承诺。操作许可与业务状态始终由服务端决定。

流程中的主按钮、当前步骤、选中项和链接统一按 01 的官方蓝色映射呈现；错误、警告和成功分别使用语义色与文字。启动／成功结果中的品牌标识遵循原图比例和蓝白组合，流程状态变化不对 Logo 滤色。

## 1. 所有写操作的共同规则

写操作经历“可编辑 → 本地校验 → 提交中 → 成功／明确失败／结果待核实”。进入第一段异步逻辑前锁定提交，避免用户在订阅授权、注册核验、云函数请求之间重复点击。

| 结果 | 界面行为 | 数据与重试 |
| --- | --- | --- |
| 校验失败 | 定位首个错误，字段旁说明，保留全部输入 | 不发请求 |
| 服务端明确拒绝 | 在当前步骤展示原因及恢复行动 | 权限、版本、冷却、名额分别处理，不无意义重试 |
| 成功且返回确认结果 | 更新界面／进入结果，清理本次草稿，失效相关缓存 | 使用返回的真实记录标识和最新状态 |
| 超时／连接中断，是否写入未知 | 显示“暂时无法确认提交结果”，保留本次上下文 | 优先核实既有记录；需要服务端幂等／结果查询支撑，不能无条件重新新建 |
| 已确认未送达 | 保留输入，提示网络恢复后重试 | 重试沿用同一业务请求标识；内容变化后才建立新的操作 |
| 离线且尚未提交 | 显示“未提交”，保留当前编辑 | 只有 action 已验证幂等、权限和时效后才能接入 outbox |

请求携带 `_requestId` 不等于服务端已具备幂等能力。自动写入重试与离线重放须有对应 action 的幂等、授权和时效保障；结果未知时提供核实路径，不得宣传“离线已报修”。

## 2. 启动、登录与权限恢复

进入小程序 → 启动页恢复登录与角色 → 进入允许的目标页；未注册 → 登录／注册 → 服务端确认身份 → 恢复目标任务。

- 初始化显示稳定品牌与真实等待反馈；失败给“重新加载”，不无限转圈或反复重启。
- 注册按基础资料、必要授权和提交结果分组，成员权限码作为可选身份升级入口，不要求普通报修用户填写。
- 权限码、环境标识和凭证不进入设计稿、示例或日志。拒绝订阅消息不影响核心登录／报修业务。
- 从未登录流程返回任务时，只恢复有必要的草稿，不绕过启动守卫。草稿按用户隔离，退出登录后清除敏感内容；若实现跨会话草稿，默认 24 小时失效并明确提示。只暂存必要表单字段，不保存权限码、凭证或由服务端恢复的成员资料。
- 运行中收到 401／403 时刷新身份并说明“身份已变化，请重新进入”，保留可安全恢复的本地内容；重新获得权限后仍需再校验任务状态。

## 3. 报修：从问题到可追踪记录

### 3.1 主路径

首页“报修设备”或报修 Tab → 搜索／选择问题 → 填写必要信息 → 核对问题、预约、费用与联系方式 → 提交报修 → 成功结果 → 查看报修进度。

顶部阶段固定为“选择问题／填写信息／核对提交”。分类中的大类、子类、具体类型是第一阶段内部渐进展开，已选路径始终可见；只剩一个有效选项时可以省略选择动作，但仍展示选中结果。

### 3.2 每阶段的交互合同

| 阶段 | 用户需要知道 | 主要行动 | 返回／异常恢复 |
| --- | --- | --- | --- |
| 选择问题 | 可输入故障描述；不确定分类可看地图；收费类型提前显示现有说明 | 选择具体问题／下一步 | 无结果提供分类入口；允许换说法；不制造未配置类别 |
| 填写信息 | 当前分类、动态必填、选填、预约规则、已有费用提示 | 下一步：核对信息 | 返回保留适用字段；分类变化仅清除不适用字段 |
| 核对提交 | 完整分类、型号／故障、预约时间、联系方式、费用与后续流程 | 提交报修 | “修改信息”回到原字段；不能为了修改重走全部分类 |
| 成功结果 | 已成功建立报修、真实单号、预约信息、下一步在哪里看 | 查看报修进度 | 次要行动“再次报修”需新建独立草稿 |

动态字段继续以 `repairCategories` 与页面现有规则为依据。笔记本型号在现有逻辑中为选填，未填时提交“未知”；视觉改造不能擅自设为必填。联系方式来自已注册资料，核对阶段让用户确认；需要修改时通过已有资料接口完成，不把申请人身份交给前端自由填写。

订阅消息在用户明确点击提交后按微信允许方式请求，先解释“用于接收受理和进度通知”；用户拒绝／关闭／只接受部分模板均继续核心提交。不要先弹“授权成功”Toast 抢占最终提交结果。

### 3.3 需要特别处理的分支

- 预约日期或时段不再可用：保留问题与描述，定位预约项，显示重新选择；不可自动改成另一个时间。
- 修改费用关联分类：重新展示费用提示和确认信息，旧确认不能沿用。
- 图片／附件只有现有接口支持时才展示上传入口；本规范不默认添加未实现的附件能力。
- 超时：保留核对页，显示待核实状态，核查是否已有同次请求记录；没有可靠查询能力时给查看待办与继续保留草稿的去向，不能谎报成功。
- 成功进入详情需要云函数返回真实 ID，或用已验证查询得到。无可靠 ID 时只能提供可验证的列表去向，不编造详情 ID。
- 成功后失效首页待办、待办列表及相关任务缓存，返回后立即看到一致信息。

## 4. 维修任务：受理、执行与完成

### 4.1 状态与操作

`pending` → 授权成员受理／管理者分配 → `inProgress` → 完成核对 → `completed`。取消是独立 action，其可用角色与来源状态必须沿用 `cancelMaintenanceTask` 的服务端校验，不画成所有状态都能任意撤销。

| 当前情况 | 展示 | 操作原则 |
| --- | --- | --- |
| 待受理 | 问题、预约、申请人必要信息、待受理状态 | 有权者出现“受理任务”；普通申请人只看自己的允许操作 |
| 进行中 | 主／附加受理人、时间和工作内容 | 负责人相关操作靠前；联系／复制为次级行动 |
| 待提交完成 | 完成影响、参与人员及接口要求字段 | 不在前端自创 EWA 分数；核对后执行既有完成 action |
| 已完成／取消 | 结果与历史信息 | 只读为主；重新报修是新任务，不重置旧任务 |

### 4.2 冲突与返回

受理前刷新当前任务；提交中按钮锁定。服务端提示已被他人受理时，刷新为真实受理人，显示“该任务已被受理”，取消本人的待受理操作，不能仍 Toast“操作失败”后保留旧按钮。

分配、移除受理人、删除等管理操作先列对象和影响；删除与取消必须区分。详情返回列表时更新对应条目，保持筛选与滚动位置。申请人详情和内部详情复用信息层次，内部操作不能泄露到普通用户页。

## 5. 值班：预选与正式确认

进入值班表 → 核对“第 N 周＋实际日期范围”与编辑状态 → 选择可选时段 → 查看个人预选摘要 → 最终核对 → 确认后显示已确认记录。

### 5.1 选择与确认

- 周次与日期范围固定可见，避免只看到“第几周”而误选日期。
- 时间列固定、日期区域局部横滚，提供文字状态及清晰的横滚提示；给个人已选列表作为不依赖表格的替代读取方式。
- 预选与已确认分组显示。必须保留“每周预选最多 3 段”的规则；计数口径与服务端一致，界面同时显示已确认数和待确认数，不能自行改变配额定义。
- 点击第 4 段时说明限制并保留前 3 段，不清空已有选择。
- 最终确认层列出全部日期、时段和“确认后不能自行取消”。主按钮“确认这些时段”，次按钮“返回修改”。
- 成功后不再显示自助撤销入口；需要调整时仅指向已有、经过确认的管理联系渠道。

### 5.2 锁与时效

| 情况 | 行为 |
| --- | --- |
| 时段被锁定／正在操作 | 显示“操作中，请稍后刷新”，不把锁当成已确认 |
| 时段已被他人占用 | 刷新该时段并标明不可选，保留其他有效选择 |
| 触发冷却 | 显示原因与服务端返回的恢复时间；没有时间时不伪造倒计时 |
| 管理关闭编辑 | 显示关闭说明；表格可浏览，预选和确认不可触发 |
| 确认遇到冲突 | 按服务端实际原子性处理；返回冲突项并重新核对，不擅自认为“其余项已成功” |
| 确认时跨周／后台切周 | 阻止对旧周盲目重试，刷新周次，保留说明让用户重新选择 |

值班预选与确认具有强时效和锁语义，不默认放入 outbox 自动重放。管理端切周、锁定与调整安排必须先核对影响范围；不能为了“减少步骤”移除后果确认。

## 6. 志愿活动：活动状态与个人参与状态分开

列表筛选 → 活动详情 → 阅读时间地点、负责人、参与安排 → 执行当前身份允许的参与／管理操作 → 显示实际结果 → 从个人待办跟踪。

现有活动状态为 `pending / inPreparation / inProgress / ended`。个人“是否参与、是否收到邀请、是否已结算”是另一维度。不能把活动“已结束”直接标记为个人“已完成／已获得工作量”。

**参与入口以已有且经过授权的 action 为依据，不假定存在面向所有成员的自助报名接口。**

- 仅负责人导入参与者的活动，页面写“参与成员／联系负责人”，不能展示无法兑现的“立即报名”。
- 若已有并可授权使用的报名 action，再实现报名中、已报名、截止、名额冲突等状态；报名截止与名额值必须来自接口。
- 邀请确认与订阅授权分开理解；拒绝通知不能被显示为拒绝活动或移出参与名单。
- 管理者修改成员、时间、地点或人均工作量前显示受影响对象；时间冲突、版本更新时保留编辑并要求重新核对。
- 取消参与、删除活动是否允许以服务端为准；有工作量影响时明确说明，不能用删除卡片动画暗示已完整处理账目。

## 7. EWA：解释口径、查看明细、谨慎修改

个人／团队工作量入口 → 选定现有数据支持的范围 → 总览 → 三科原始值及加权贡献 → 具体业务明细。管理角色另有调整／导出入口，按已有权限实现。

加权公式固定为：维修×0.5＋志愿×0.4＋值班×0.1；单科目上限 300。示例：维修 100、志愿 50、值班 20，对应加权贡献 50、20、2，总分 72。图表标题必须说明展示“原始工作量”还是“加权贡献”；不能把三科直接相加显示为总分，也不能以 `900` 作为加权总分上限。

- 详情显示数据更新时间、范围与单位；接口没有学期／时间筛选时不放假筛选器。
- 0 值写 0，缺失写“—”，计算失败给重试，不能全归成“暂无数据”。
- 手动修改显示原值 → 新值、涉及对象与原因要求；先校验现有上限／接口约束，再提交；成功后从后端重读，不只改图表。
- 更新汇总和导出显示进度状态，不承诺固定秒数；失败可重试，不清除当前筛选。
- 导出只向有权者提供，并沿用已有下载／打开能力；不能在普通用户页面输出全员数据。

## 8. 组员管理：资料修改、任免与移出

业务依据：[组员管理](../../member-management.md)。本设计保留现有边界，不新增账号、添加／恢复成员或候选人搜索功能。

名单搜索／部门角色筛选 → 详情 → 按服务端返回 `permissions` 显示操作。组长只管理允许的普通组员；管理员可按规则管理组长及任免；不能管理自己或管理员身份。

### 8.1 资料编辑

详情“编辑资料” → 底部抽屉 → 修改允许字段 → 字段校验 → 保存 → 成功关闭并刷新详情。

修改过的内容离开时确认是否放弃；保存失败保留全部字段。收到版本冲突时显示“资料已被更新”，允许查看最新版本并重新核对，不能静默覆盖。部门切换保留已有一小时冷却规则，按服务端返回显示恢复时间。头像仍由用户本人维护。

### 8.2 任免

选择任免 → 确认目标成员、原角色、新角色及权限影响 → 提交 → 刷新真实角色。普通资料保存不额外弹确认；任免属于权限变化，保留明确确认。

### 8.3 移出

填写原因 → 核对成员、原因和影响 → 确认移出 → 成功刷新名单与权限投影。

确认层必须说明：移出后仍保留普通账号、历史业务和全部工作量，不能通过旧权限码自行恢复。禁止出现“永久删除账号／清空工作量”等错误文案。

如果存在未完成维修、未来或未结束值班、未结束活动等交接阻塞，在同一弹窗展示具体列表和去向；保留原因与请求标识。不能自动取消相关任务，也不能点击重试绕过交接校验。提交中禁止重复点击和误关闭；失败后能在原步骤修正并继续。

## 9. 消息、待办与外链

- “未读”描述阅读状态，“待处理”描述业务行动。打开消息不自动标记任务完成；待反馈消息继续执行其明确确认逻辑。
- 消息列表显示标题、摘要、时间、阅读状态；有业务记录时进入详情，无记录时原地展开内容。
- 列表“全部已读”若保留，必须与完成全部待办完全区分，不能共享含糊的“全部处理”。
- 工具类外链明确写“打开维修手册”或“复制链接”；打开失败保留说明和可行替代。仅当平台及已配置域名支持时使用 web-view，否则沿用现有外链能力，不假设任意飞书页面都能内嵌。

## 10. 跨流程一致性

成功后通过现有事件总线／SWR 失效相关缓存，订阅在 `onUnload` 退订。需要显示“已同步”时必须有实际服务端确认；后台刷新不抢焦点、不重置输入。退出登录或角色降级时清理敏感缓存、草稿与不能继续执行的队列项，避免旧身份操作被自动重放。
